# CAD Advisory — outstanding issues from outside black-box analysis

**Subject:** CAD 0.5.0 single-file test build (Rust core as `core.wasm` + browser shell)
**Date:** 2026-10-08
**Nature:** Analysis only. Nothing was built or changed.

## Clean-room statement (read first)

- Every finding comes from **observing this build's own behaviour** (its public entry points, its saved files, its on-screen results) and from **published format knowledge** (the public DXF reference and public DWG documentation).
- **No third-party source code, no other project's behaviour, and no output of any other CAD program is used or referenced here.** None was used to reach these conclusions.
- Recommendations are stated as **symptoms, measurements and required outcomes**, never as implementations. Design the fixes yourself from your own code and the public specs.
- Hypotheses about causes are labelled as hypotheses; confirm them in your own source.
- Suggested hygiene: keep all test fixtures hand-authored by you (or generated by your own core); log the provenance of each fixture; do not feed the core files produced by other programs' code unless your policy already permits it.

## P1-1  Entities-only DXF opens as an empty drawing with no warning

**Reproduction (hand-written file).**
```
0 SECTION / 2 ENTITIES
0 LINE   (layer 0, 0,0 → 10,10)
0 CIRCLE (layer HOLES, centre 5,5, r 2)
0 ENDSEC / 0 EOF
```
`open` succeeds and `info.summary` reports `Objects: 0 … Model space: 0 entities drawn`. `display()` returns an empty list. Editing commands then fail with "the drawing has no model space block table".

**Why it matters.** The public DXF reference allows files with only an ENTITIES section; such files are common from simple exporters. A silent empty open reads to users as data loss.

**Required outcomes.**
1. Entities with no resolvable owner, in a file with no block tables, are treated as model space and drawn.
2. If any entity records are read but none are placed, the open reports it ("N entities found, none placed") rather than "0 objects".
3. A drawing opened this way gets a model-space container on first edit instead of failing.

**Test both variants** (no tables at all; tables present but entities lacking an owner pointer) using files you write from the DXF reference.

## P1-2  Per-edit cost scales with drawing size (memory and time)

**Measured through the core's own API, 2026-10-08.**

| Drawing | After N single edits | Memory | Time per edit |
|---|---|---|---|
| 2,584 objects | 25 → 100 | 62 → 158 MB, then flat | 3–13 ms |
| 20,504 objects | 25 → 75 | 476 → 1,208 MB, then flat ≈1.2 GB | ≈127 ms, falling to ≈60 ms |
| empty, 6,000 sequential `line` commands | 6,000 | 347 MB | 11 s total (≈1.9 ms/edit, rising) |
| empty, 2,000 `line` commands inside one `begin`/`end` | 2,000 | 1,789 MB | 12.6 s |

Observations: roughly 18 MB per edit at 20k objects; a grouped command grows far faster than ungrouped ones (about 4× the memory per edit at 1,000 and 15× at 2,000); memory stops growing once a ceiling is reached.

**Hypothesis (confirm in source).** Each edit keeps a whole-drawing copy for undo/change history, and grouped edits keep more than one copy.

**Required outcomes.** Memory per edit independent of drawing size; a 20k-object drawing editable for thousands of edits inside a stated memory budget (e.g. < 300 MB); grouped commands linear in the number of operations. Add a history memory cap with oldest-first eviction. Keep the operation-log direction from the roadmap: store the change, not the whole drawing.

## P1-3  Crash recovery misses out-of-memory and large-address failures

**Observed.** Once core memory passes 2 GiB, result-buffer addresses returned by the core arrive in the shell as negative numbers and `new Uint8Array(buffer, ptr, len)` throws `RangeError: Start offset -2145636008 is outside the bounds of the buffer`. The shell's guard only recovers from `WebAssembly.RuntimeError`, so this error propagates and the page stops responding instead of restarting the core as designed.

**Required outcomes.**
1. All pointers/lengths from the core are read as unsigned 32-bit values in the shell.
2. The guard treats `RangeError`, memory-grow failure and `WebAssembly.RuntimeError` alike: mark crashed, restart, reopen drawings from their last saved bytes, tell the user.
3. A soft limit warns the user (and refuses further growth) well before 2 GiB. Fixing P1-2 reduces how often this is reachable.

## P2-1  Hit-testing cost at scale

At 20,504 objects, a `pick` query took ≈23 ms while a `snap` query took ≈2.6 ms. Pick runs on every pointer move for hover, so at this size it alone approaches a frame budget. Required outcome: pick comparable to snap (< 5 ms at 20k), e.g. by sharing whatever acceleration structure snap uses.

## P2-2  Full display-list refresh after every edit

After each edit the shell calls `display()` for the whole drawing (≈1.3 MB at 20k) and recomputes per-item bounds in JavaScript. Required outcome: the core reports only changed handles (added/removed/modified), and the shell patches its list. Redraw itself is healthy (≈32 ms for a full 20k redraw, software-rendered), so the win is in refresh, not paint.

## P2-3  Unit label inconsistent after DWG round trip

The sample drawing (millimetres, `insunits = 4`) saved to DWG and reopened reports `insunits = 4` in the info record but `Units: unknown` in the human-readable summary. DXF, binary DXF and .cad round trips report millimetres. Required outcome: the summary reflects the same unit value the info record carries, for every format.

## P3-1  Keep the robustness you have

**Measured positives, retain with tests.** 1,200 deliberately damaged copies (truncated, bit-flipped and overwritten DWG, DXF, binary DXF and .cad) plus 200 random byte buffers: 0 panics; every bad input returned a descriptive error; all five formats round-tripped the 54-object sample with no loss. Turn this into a permanent fuzz target in CI with a seed corpus of your own files, and add a regression test for every future failure.

## P3-2  Scope gaps (not defects)

Offset, Trim and Fillet are visibly disabled ("not built yet"). Confirm they remain on the roadmap; they are the main reason the editing set feels incomplete beyond the core drawing/transform commands.

## Suggested order
1. P1-3 (stability) and P1-1 (blank opens), in parallel.
2. P1-2 (memory model), since P1-3's limit and P2-2's patching both depend on how history is stored.
3. P2-1, P2-2, P2-3; then P3.

## Acceptance checks
- Hand-written entities-only DXF draws two entities and accepts an edit.
- 20k-object drawing: 500 edits stay under the memory budget; no `RangeError` path reachable; forced out-of-memory restarts the core and reopens the drawing.
- Pick < 5 ms at 20k objects.
- Fuzz run completes with zero panics.
